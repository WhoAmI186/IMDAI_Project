**Inspection Date:** September 28, 2026  
**Inspected Files:**
1. `dataset/merged_datasets.duckdb` (4.22 GB / 4,539,822,080 bytes)
2. `dataset/impact_assessment.duckdb` (2.26 MB / 2,371,584 bytes)
**Access Mode:** Read-Only (`read_only=True`), no data modified, transformed, or merged.

---

## Executive Summary

This report presents a thorough, read-only inspection of the two DuckDB databases located in the `dataset/` directory: `merged_datasets.duckdb` and `impact_assessment.duckdb`. The inspection was conducted without modifying either database, deleting or transforming any data, merging tables, or touching raw PCAP files.

- **`merged_datasets.duckdb` (Primary Data Source)** is an extensive cyber-physical testbed dataset encompassing 11 relational tables with over **24 million network packets**, **1.55 million packet modification events**, **583,000 process telemetry data points** (battery, PV solar, wind turbine, and power demand), **24,000 PLC syslog alerts**, and **436 multi-agent LLM attack sessions** across 6 distinct recording runs (1 normal baseline run and 5 multi-agent adversarial attack runs).
- **`impact_assessment.duckdb` (Evaluation / Context Dataset)** contains a single specialized table (`judge_results`, 1,009 rows) documenting an automated LLM-as-a-judge evaluation (using `kit.mistral-small-4-119b-a8b`) of whether specific attack execution steps caused measurable physical deviations in grid process signals, including pre/during/post attack time-series slices and ground-truth impact flags.

### 2.3 Deep Dive: Purpose & Content Breakdown

Based strictly on the actual schema, sample records, and execution data in `impact_assessment.duckdb`, the table `judge_results` serves as an **automated cyber-physical impact evaluation database**. It contains:

1. **Attack Impact Information:**
   - `delta_observed_during_active` (BOOLEAN): Ground-truth indicator of whether the attack succeeded in producing an observable physical change in the target signal during the active attack duration.
   - `after_similar_to_before` (BOOLEAN): Evaluates whether the system signal returned to its baseline state after the attack ended (resilience / stealth / recovery).
   - `delta` (DOUBLE): The intended or injected numerical perturbation magnitude (e.g. +180.0 W target power, -111.17 W power, +17.25 rpm speed).

2. **System Impact Metrics:**
   - `active_duration` (DOUBLE): Duration of the attack's active window in seconds (ranging from ~8s to ~18s).
   - `before_len`, `during_len`, `after_len` (INTEGER): Number of sensor telemetry observations captured in the pre-attack, attack, and post-attack time windows.
   - `connection_table` (VARCHAR): Identifies the affected physical process subsystem (`battery_process_data`, `pv_process_data`, `wind_process_data`).
   - `signal_name` (VARCHAR): Identifies 24 distinct physical process signals evaluated.

3. **Evaluation Results & LLM Metadata:**
   - `model` (VARCHAR): Evaluator model identity (`kit.mistral-small-4-119b-a8b`).
   - `inference_duration` (DOUBLE): Evaluation run time in seconds per step (average ~3.3s).
   - `usage` (STRUCT): Token accounting (`input_tokens`, `output_tokens`).
   - `thinking` (VARCHAR): Chain-of-thought reasoning of the judge explaining how outliers, noise, transitions, and baseline drift were distinguished from genuine cyber-attack perturbations.
   - `human_prompt` (VARCHAR): Complete prompt template sent to the model containing the CSV-formatted time-series data.

4. **Embedded Data Series (Derived Analysis):**
   - `before_df`, `during_df`, `after_df` (JSON arrays): Embedded time-series slices `[{ts, sensor_value}, ...]` extracted from the process tables around the attack window.

## 5. Recommendations for Phase 1 & Project Architecture

### Recommendation for `merged_datasets.duckdb`: **A. Used as a primary data source**

- **Rationale:** This is the ground-truth experimental repository containing raw and semi-processed cyber-physical telemetry across the entire smart grid testbed. It houses the complete operational history of process signals (battery, PV, wind, demand), complete network communication (24M packets), PLC security logs (24K alerts), and exact ground-truth packet injection markers (`attack_datamod_history`).
- **Phase 1 Strategy:**
  1. Extract process telemetry tables (`battery_process_data`, `pv_process_data`, `wind_process_data`, `demand_process_data`) and align them on a unified 0.5s or 1.0s time grid.
  2. Leverage `dataset.id` = `'21c851bc-384f-5b81-8747-6dcacdceff35'` (`20260225_normal`) strictly for training baseline normal behavior models.
  3. Map `attack_datamod_history` and `exec_steps` timestamps directly onto the process time series and network flow features to establish precise, timestamped intrusion ground-truth labels.

### Recommendation for `impact_assessment.duckdb`: **B. Used only for evaluation / context**

- **Rationale:** `impact_assessment.duckdb` is not a primary sensor capture. Rather, it represents a downstream, derived evaluation performed two months post-experiment using an LLM evaluator (`kit.mistral-small-4-119b-a8b`). While its labels (`delta_observed_during_active`, `after_similar_to_before`) and time-series slices are highly valuable for validating whether an attack caused observable physical disruptions, it should not be mixed into primary training pipelines as raw ground truth.
- **Strategic Utility:**
  1. **Impact Validation:** Use `judge_results` to separate *stealthy/ineffective attacks* (where packet injection occurred but physical process signals were unaffected, 58.7% of cases) from *high-impact physical attacks* (where process signals were actively perturbed, 36.0% of cases).
  2. **Secondary Evaluation Metric:** Evaluate whether our anomaly detection models detect high-impact attacks faster or with higher confidence than subtle or ineffective attacks.
  3. **Contextual Enrichment:** Cross-reference LLM judge reasoning (`thinking`) when analyzing false positives or false negatives during Phase 2 model evaluation.
